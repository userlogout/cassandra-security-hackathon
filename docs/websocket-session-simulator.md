# Cassandra API и WebSocket

## Что установлено о Cassandra

| Наблюдение или источник | Что подтверждает | Что остаётся неизвестным |
| --- | --- | --- |
| Документация описывает вход в терминал и штатный выход с переходом к форме авторизации. | Порядок работы пользовательского интерфейса. | Как сервер отзывает сессии и что происходит с уже открытыми сокетами. |
| В проверке сессии после выхода вкладка AI сохраняла ранее загруженный диалог. | В материалах проекта зафиксированы HTTP-запросы проверки авторизации и SSO виджета. Приложение А описывает требования к работе при потере связи и переподключении. | Успешную начальную HTTP-проверку в авторизованной сессии и ожидаемое свойство системы. | Реализацию WebSocket-переподключения, возобновления подписок и обработки повторных команд. |

Источники — [вход в терминал](https://docs.lite-invest.com/cassandra/main-functions/connecting), [основное окно и выход](https://docs.lite-invest.com/cassandra/interface), [проверка сессий](session-management-test-results.md), [диагностика виджета](cassandra-ai-diagnostics.md), [анализ требований](security-criteria-analysis.md).

**По доступным материалам ни один конкретный механизм восстановления WebSocket не подтверждён.** Записи рукопожатий, разрывов и последующих подключений в изученных материалах отсутствуют. Не установлены наличие автоматического reconnect, интервалы и пределы повторных попыток, heartbeat, восстановление подписок по снимку или позиции в потоке, дедупликация команд и перепроверка сессии на каждом сообщении. HTTP-авторизация и SSO сами по себе не подтверждают эти механизмы.

## Запуск локального стенда

Требуется Node.js 22 или новее. Из корня репозитория:

```sh
npm --prefix defense ci --ignore-scripts
npm --prefix defense test
npm --prefix defense start
```

Тесты сами запускают сервер на свободном порту loopback. Команда `start` запускает отдельный экземпляр на `127.0.0.1:8765`. Остановка — Ctrl+C. После установки зависимости интернет для работы стенда не нужен.

| Точка входа | Назначение |
| --- | --- |
| `POST /session` | Создать вымышленную сессию и получить локальный `sessionId`. |
| `POST /command` | Записать синтетическое намерение. Передать `sessionId` в заголовке `x-demo-session` и команду в JSON. |
| `ws://127.0.0.1:8765/stream` | Открыть WebSocket с тем же заголовком и отправлять команды текстовыми JSON-сообщениями. Программный пример клиента есть в [интеграционном тесте](../tests/session-simulator.test.mjs). |
| `DELETE /session` | Завершить вымышленную сессию по заголовку `x-demo-session`. |

Пример синтетической команды:

```json
{"type":"record_mock_intent","commandId":"DEMO-1","symbol":"SIM-ALPHA"}
```

Операция увеличивает только счётчик ревизий в памяти для единственного вымышленного счёта. Все сетевые точки входа запускаются с защитой. Варианты с выключенными проверками доступны в модульных тестах ядра. Симулятор работает в одном процессе, проверяет сессию непосредственно перед применением команды и использует общую таблицу квитанций для HTTP и WebSocket. Запись побочного эффекта и квитанции выполняется в одном синхронном обработчике. При перезапуске процесса сессии и квитанции сбрасываются. Закрытие уже открытого сокета в модели происходит при первом сообщении после завершения сессии.

## Результаты тестов

| Сценарий | Без соответствующей проверки в модели | С защитой |
| --- | --- | --- |
| Повтор команды после переподключения | Две обработки, ревизии 1 и 2. | Возвращается первая квитанция с прежней ревизией и признаком повтора. Тот же идентификатор с другим инструментом отклоняется с `409`. |
| Сообщение по соединению после выхода | Уже открытый обработчик принимает команду. Новое подключение отклоняется. | Открытый сокет получает `401` в JSON и закрывается с кодом `1008`. HTTP-команда отклоняется с `401`, повторное рукопожатие с завершённой сессией — с `403`. |

Запуск на Node.js 26.12.1 — **5 из 5 тестов прошли**. Интеграционный тест на loopback подтвердил повторное подключение, общую квитанцию для параллельных повторов по HTTP и WebSocket и отзыв сессии. Cassandra и реальные торговые системы в тестах не использовались.

## Какие доказательства нужны для вывода о Cassandra

На согласованном тестовом стенде с вымышленным счётом или по внутренним журналам команды Cassandra:

- Сопоставить события разрыва, нового рукопожатия и восстановления подписок по времени и идентификаторам соединений. Это покажет, какие механизмы восстановления фактически работают.
- Сверить идентификатор логической команды, её подтверждения и журнал применения после контролируемого сбоя связи. Для подтверждения дефекта нужны два зафиксированных применения одной команды, поскольку повторная доставка сообщения сама по себе недостаточна.
- Сопоставить момент серверного отзыва сессии и журнал решений по сообщениям открытого канала. Признак нарушения — новый защищённый ответ или зафиксированное действие после отзыва, относящееся к завершённой сессии. Остаток старых данных в интерфейсе этого не доказывает.
