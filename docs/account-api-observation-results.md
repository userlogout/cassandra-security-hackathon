# Cassandra — штатные запросы разделов счёта

21 ноября 2026 года. Пассивное наблюдение XHR и fetch через Playwright MCP в текущей авторизованной сессии. Открыты представления «Позиции», «Заявки», «Все» и «Закрытые» на `/transactions`, а также «Финрез» на `/fin-rez`. В качестве представления баланса использованы поля «Средства» и «Доступно» в «Финрезе». Сохранялись маршруты, методы, статусы и факт наличия заголовков. Значения заголовков, идентификаторы, суммы и тела ответов в отчёт не включены. Запросы и WebSocket-сообщения не изменялись. Торговые операции и выход из сессии не выполнялись.

| Представление | Запросы к `api-cassandra.lite-invest.com` | Наблюдение |
| --- | --- | --- |
| Общая загрузка | `GET /api/Account`, `GET /api/Authentication/test` | Оба вернули HTTP 200 при загрузке «Сделок» и «Финреза». В обоих присутствовал `Authorization`, заголовок `Cookie` не наблюдался. |
| Баланс и доступные средства | `POST /hubs/finrez/negotiate` | HTTP 200 при открытии «Финреза». Связь канала с конкретными полями таблицы по содержимому сообщений не проверялась. |
| Позиции | `POST /hubs/positions/negotiate` | HTTP 200 уже при загрузке «Сделок». Переключение на «Позиции» не выявило отдельного запроса чтения в окне наблюдения. |
| Заявки | `GET /Order/[redacted]/[redacted]`, `POST /hubs/order/negotiate`, `POST /hubs/orderstoplimit/negotiate`, `POST /hubs/orderconditional/negotiate` | HTTP 200. GET наблюдался при открытии «Заявок» с `Authorization` и без `Cookie`. Назначение двух скрытых сегментов не установлено. |
| История операций | `POST /hubs/trade/negotiate` | HTTP 200 при переключении на «Все». При переключении на «Закрытые» отдельного запроса чтения в окне наблюдения не зафиксировано. Полнота истории и источник данных «Закрытых» не установлены. |

Во всех перечисленных запросах согласования каналов присутствовали `Authorization` и `Cookie`. Согласование канала показывает этап подключения. По нему нельзя определить, какие данные передаются, для какого счёта разрешена подписка и какие проверки выполняет сервер. Успешный `/api/Authentication/test` показывает штатный вызов проверки с действующей сессией. Реакция сервера на отсутствие авторизации или отсутствие доступа к конкретному счёту в этом этапе не проверялась.

### Гипотезы для проверки по серверному коду и тестам

1. **Проверка прав на объект в обработчике чтения заявок.** Запрос `GET /Order/[redacted]/[redacted]` содержит два сегмента пути, которые скрыты в отчёте. В коде стоит установить их назначение и проверить, ограничивает ли обработчик выборку счетами текущего пользователя. Наблюдение относится только к успешному запросу собственного интерфейса.
2. **Проверка прав при подписке на данные счёта.** Финрез, позиции, заявки и сделки используют отдельные каналы. Видны запросы согласования с авторизацией, но по ответам HTTP 200 область доступа к данным установить нельзя. В коде и тестах стоит проверить, что при подписке и маршрутизации событий учитываются полномочия на счёт.

Нарушений разграничения доступа по результатам этого этапа не подтверждено. Выводы предыдущего исследования WebSocket учитывают, что в обеих попытках пользователь вручную входила на экране /auth.
